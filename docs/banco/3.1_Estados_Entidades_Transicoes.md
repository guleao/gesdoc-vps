## 1. Entidades principais

| Entidade | O que representa | Observações |
|---|---|---|
| `regra_documento` | Cada um dos 116 tipos de documento da matriz (ex: "Vale Alimentação", "GFD + RE + CP") | Vem direto do índice da planilha: categoria, origem (SharePoint/Factorial), destino (Atlas/Bernhoeft), periodicidade, prioridade MVP |
| `entidade` | Colaborador (CPF) ou Empresa/Contrato (CNPJ) ao qual o documento se aplica | Tipo enum: `colaborador` \| `empresa` |
| `contrato_projeto` | Vínculo contratual/obra, quando o documento é por obra (ex: RRT, PGR, AVCB) | Nem todo documento tem; nullable |
| `documento` | Instância concreta de um documento — cruzamento de `regra_documento` + `entidade` + competência/evento | Estado atual vive aqui |
| `versao_documento` | Cada arquivo que chega para um `documento` (original, correção, reenvio) | Hash do conteúdo, timestamp, origem (SharePoint/Factorial) |
| `pacote` | Agrupamento de itens "+" que precisam ser mesclados antes do envio (ex: RelBen + Boletim + Comprovante) | Só existe para `regra_documento.grupo = 'pacote'` |
| `pacote_item` | Relação N:N entre `pacote` e `versao_documento` | Controla o que falta pro pacote fechar |
| `destino_envio` | Um par (`documento`, portal destino) — Atlas e Bernhoeft são controlados **de forma independente** | Um documento pode estar aprovado no Atlas e pendente no Bernhoeft ao mesmo tempo (ticket 6.9) |
| `tentativa_envio` | Cada tentativa de envio de um `destino_envio` | status, timestamp, payload/resposta, erro |
| `protocolo` | Número/protocolo devolvido pelo portal quando aceito | 1:1 com `tentativa_envio` bem-sucedida |
| `alerta` | Pendência/atraso vinculado a `documento` ou `destino_envio` | Consumido pela Macro 7 (e-mail/WhatsApp) |
| `auditoria` | Log append-only de toda transição de estado | Nunca é editado, só inserido |

**Por que separar `documento` de `destino_envio`:** a matriz mostra vários documentos com dois destinos (ex: item 78 — ASO, vai para Atlas *e* Bernhoeft). Se o estado morasse só no documento, não daria pra representar "aprovado num portal, rejeitado no outro" — que é uma pergunta explícita que a Macro 1 já registrou ("O documento pode estar aprovado num portal e pendente no outro?").

## 2. Máquina de estados

### 2.1 Estado do `documento` (independente de destino)

```
AUSENTE
  │  evento: novo_arquivo_detectado (SharePoint/Factorial)
  ▼
LOCALIZADO
  │  evento: validacao_iniciada
  ▼
EM_VALIDACAO ──(regra falhou)──► INVALIDO ──► (volta a AUSENTE ou fica em alerta manual)
  │  evento: validacao_ok
  ▼
VALIDO
  │
  ├─(regra_documento.grupo = 'simples')──────────────► PRONTO_PARA_ENVIO
  │
  └─(regra_documento.grupo = 'pacote')
        ▼
    AGUARDANDO_COMPOSICAO ──(faltou item)──► ALERTA_PACOTE_INCOMPLETO
        │  evento: pacote_completo (todos os pacote_item presentes)
        ▼
    COMPOSTO (merge PDF executado — serviço da Macro 5)
        ▼
    PRONTO_PARA_ENVIO
```

A partir de `PRONTO_PARA_ENVIO`, o controle passa para um ou mais `destino_envio` (um por portal aplicável, conforme `regra_documento.destino_atlas` / `destino_bernhoeft`).

### 2.2 Estado do `destino_envio` (por portal)

```
PENDENTE_ENVIO
  │  evento: envio_realizado (tentativa_envio criada)
  ▼
ENVIADO
  │  evento: retorno_recebido
  ▼
AGUARDANDO_RETORNO ──(timeout)──► ALERTA_SEM_RETORNO
  │
  ├──► APROVADO (protocolo gerado)
  ├──► REJEITADO (motivo capturado) ──► PENDENTE_CORRECAO ──(nova versao_documento)──► PRONTO_PARA_ENVIO
  └──► PENDENTE_INTERVENCAO (ex: reCAPTCHA no Bernhoeft — fila de revisão humana, Macro 5 ticket 5.7)
```

`documento.estado_consolidado` é uma coluna derivada (view ou trigger) que resume os `destino_envio` — por exemplo `PARCIALMENTE_APROVADO` quando Atlas = APROVADO e Bernhoeft = AGUARDANDO_RETORNO. Isso evita reenviar para um destino já aprovado quando o outro ainda está pendente.

### 2.3 Eventos que disparam transição

| Evento | Origem | Observação |
|---|---|---|
| `novo_arquivo_detectado` | Webhook/polling SharePoint, API Factorial | Macro 4 |
| `validacao_concluida` | Serviço de validação (Macro 5) | integridade, metadados, assinatura |
| `pacote_completo` | Trigger interno ao inserir `pacote_item` | recalcula se todos os itens do pacote chegaram |
| `envio_realizado` | Workflow n8n → Atlas/Bernhoeft | cria `tentativa_envio` |
| `retorno_recebido` | Callback ou polling do worker Bernhoeft / integração Atlas | atualiza `destino_envio` |
| `prazo_vencido` | Agendamento 2h (07h–19h) + rotina diária (Macro 7 ticket 7.1) | gera `alerta` |
| `correcao_reenviada` | Nova `versao_documento` para um `documento` em `PENDENTE_CORRECAO` | reabre o fluxo só para os destinos rejeitados |

## 3. Regras de idempotência

1. **Chave de conteúdo:** `hash = sha256(arquivo_bytes)`. Gravada em `versao_documento.hash`. Se um arquivo idêntico chegar de novo (reprocessamento do SharePoint, por exemplo), a versão é reconhecida como duplicata e **não** gera novo ciclo de validação/envio.
2. **Chave de negócio composta:** `(regra_documento_id, entidade_id, competencia_ou_evento, contrato_projeto_id)` — identifica *qual* documento é, independente do arquivo físico. É essa chave que decide se um arquivo novo é uma "primeira versão" ou uma "correção" de um documento já existente.
3. **Lock distribuído (Redis):** durante o processamento de uma chave de negócio, um lock (`SETNX` com TTL) evita que duas execuções concorrentes do loop de 2h processem o mesmo documento ao mesmo tempo — importante porque o agendamento roda a cada 2h das 07h–19h e pode haver reprocessamento manual simultâneo.
4. **Envio já aceito não é repetido:** antes de qualquer `tentativa_envio`, o workflow verifica se já existe `destino_envio.estado = APROVADO` para aquele par (documento, portal). Se sim, pula — mesmo que o documento tenha sido "tocado" de novo por outro motivo (ex: pacote recomposto por causa de outro item).
5. **Reprocessamento pós-queda (ticket 7.6, contingência):** ao retomar depois de uma interrupção, o sistema reconstrói o estado a partir de `auditoria` (append-only) — nunca assume que uma tentativa sem retorno registrado falhou; ela entra em `AGUARDANDO_RETORNO` e é revalidada, não reenviada.

## 5. O que fazer e como fazer — passo a passo do ticket 3.1

**O que é o entregável do 3.1:** não é código, é o *desenho* que os tickets seguintes vão implementar — as tabelas da seção 1, o diagrama de estados da seção 2, os eventos da seção 3 e a idempotência da seção 4, todos já validados contra os 36 documentos reais (seção 4). Como já cruzei o índice do xlsx com a máquina de estados, o ticket 3.1 está **funcionalmente completo** neste documento. O que falta é validação sua e formalização.

**Como fechar o ticket 3.1 (nesta ordem):**

1. **Valide a lista de 36 contra a planilha original** — confira se os `indice_origem` da seção 4 batem exatamente com os 36 que você marcou no print (é a mesma lista; eu apenas trouxe as colunas completas de origem/destino/periodicidade que não apareciam na captura de tela).
2. **Confirme os 2 casos "dois portais" (78 e 79)** — são o ponto mais delicado do modelo, porque exigem `destino_envio` duplicado com aprovação independente. Se a Equatorial não usar Bernhoeft para ASO/Ficha de Registro, esses dois viram "simples" e o modelo fica ainda mais simples.
3. **Confirme os 4 "com validade" (64, 81, 82, 84)** — são os que vão alimentar o calendário de alerta (ticket 3.5). Se houver mais algum documento da lista de 36 com validade que a planilha não deixou explícito, é a hora de marcar.
4. **Resolva a leitura de "Portal Externo"** (nota da seção 4) — confirmação rápida, sem isso ainda dá pra seguir com a leitura "informativo" que assumi.
5. **Registre o fechamento formal**, como o padrão que vocês já usam no documento de entrega de Macro 1/2: Status (demonstrado/pendente), responsável (Evilásio), data.
