Implantação da sincronização Factorial

Oi, Augusto! Este é o guia para subir no servidor o serviço que vem depois da sua captura de pendências. Siga na ordem: cada passo diz o que conferir antes de ir para o próximo.

Repositório: github.com/evilasioferreira/gestao-documental-equatorial Servidor: Linux (Ubuntu 22.04+), Python 3.10+ Tempo estimado: ~1 hora

Visão geral

O processo tem três etapas. A sua já roda; esta é a do meio; o envio ao Atlas é a próxima a ser feita.

O que o serviço faz com cada pendência atrasada da Factorial

  1. Valida o empregado na Factorial (fonte da verdade). Se o CPF não existe, ou se o Atlas cobra rescisão de alguém que está ativo, marca como divergente e não busca nada.
  2. Busca os documentos na API da Factorial e casa pelo nome do arquivo, pasta e data. O conteúdo dos documentos não é aberto.
  3. Baixa os arquivos.
  4. Une num PDF único quando o Atlas exige o pacote (tabela abaixo). Documentos simples seguem com o arquivo original.
  5. Grava no Neon estado, caminho do arquivo, tamanho e hash SHA-256. Quando falta algo, registra um alerta com o motivo.
doc_idPacote (um único upload)Ordem no PDF
8Aviso e recibo de fériasaviso → recibo → comprovante
9TRCTTRCT → termo de quitação assinado → comprovante
10GFD rescisóriaguia → comprovante

O que você recebe

  • Acesso ao repositório (é privado): convite do GitHub para a sua conta.
  • Credenciais, por canal seguro e separado deste guia: a DATABASE_URL do Neon (produção) e a chave da Factorial.
  • A SECRET_KEY você mesmo gera no servidor (passo 3).
Copie e cole a chave da Factorial; nunca digite Ela tem centenas de caracteres, e um único caractere trocado (l/I, 0/O, 5/S) faz a Factorial responder 401. Já aconteceu durante o desenvolvimento.

2Instalação

Crie um usuário de serviço (sem login), a pasta dos documentos e a pasta de logs:

bash
sudo useradd --system --create-home --home-dir /opt/gesdoc --shell /usr/sbin/nologin gesdoc
sudo mkdir -p /srv/gesdoc/downloads /var/log/gesdoc
sudo chown -R gesdoc:gesdoc /srv/gesdoc /var/log/gesdoc
sudo chmod 700 /srv/gesdoc/downloads

Clone o repositório e instale as dependências num ambiente virtual. Como o repositório é privado, no git clone use um Personal Access Token do GitHub como senha (ou uma deploy key SSH só de leitura).

bash
sudo -u gesdoc git clone https://github.com/evilasioferreira/gestao-documental-equatorial.git /opt/gesdoc/app
cd /opt/gesdoc/app
sudo -u gesdoc python3 -m venv .venv
sudo -u gesdoc .venv/bin/pip install -r requirements.txt
conferir
sudo -u gesdoc .venv/bin/python -c "import pypdf, PIL, flask; print('ok')"

imprime ok.

Daqui em diante, tudo roda dentro de /opt/gesdoc/app Se aparecer No such file or directory para requirements.txt, .env ou um .py, o terminal está em outra pasta: rode cd /opt/gesdoc/app.

3Configuração (.env)

Gere a SECRET_KEY:

bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"

Crie o .env a partir do modelo e preencha:

bash
sudo -u gesdoc cp .env.example .env
sudo -u gesdoc nano .env
.env
DATABASE_URL=postgresql://usuario:senha@ep-....neon.tech/neondb?sslmode=require
SECRET_KEY=<valor gerado acima>
FACTORIAL_API_URL=https://api.factorialhr.com/api/2026-10-01/resources
FACTORIAL_API_KEY=<chave da Factorial>
FACTORIAL_PASTA_DOWNLOAD=/srv/gesdoc/downloads

Proteja o arquivo:

bash
sudo chmod 600 .env

Testar as duas conexões

Neon
sudo -u gesdoc .venv/bin/python -c "from dotenv import load_dotenv; load_dotenv(); import os, psycopg2; psycopg2.connect(os.environ['DATABASE_URL']).close(); print('Neon ok')"
Factorial
sudo -u gesdoc .venv/bin/python -c "from dotenv import load_dotenv; load_dotenv(); import os, requests; r = requests.get(os.environ['FACTORIAL_API_URL'] + '/employees/employees?limit=1', headers={'x-api-key': os.environ['FACTORIAL_API_KEY']}, timeout=30); print('Factorial', r.status_code)"

Neon ok e Factorial 200. Se a Factorial der 401, a chave está errada (veja o aviso da seção anterior).

4Preparar o banco (uma vez só)

4.1 — Regras dos pacotes

No SQL Editor do Neon (branch production), os doc_id 2 a 10 devem estar com requer_composicao = true:

sql
SELECT doc_id, nome, requer_composicao FROM documento_regras WHERE doc_id BETWEEN 2 AND 10 ORDER BY doc_id;

Se algum estiver false:

sql
UPDATE documento_regras SET requer_composicao = (doc_id BETWEEN 2 AND 10), atualizado_em = now()
WHERE requer_composicao IS DISTINCT FROM (doc_id BETWEEN 2 AND 10);

4.2 — Regerar os arquivos neste servidor

Não pule este passo As pendências já marcadas como prontas (COMPOSTO/LOCALIZADO) foram processadas em outra máquina, ou pelo n8n, que não guardava arquivo. Os PDFs delas não existem neste servidor. Em 14/10/2026 eram 20: 8 COMPOSTO + 12 LOCALIZADO.

Veja quantas são:

sql
SELECT estado, count(*) FROM documentos
WHERE estado IN ('COMPOSTO', 'LOCALIZADO') AND caminho_origem NOT LIKE '/srv/gesdoc/%'
GROUP BY 1;

Volte-as para a fila; o serviço baixa da Factorial e compõe tudo de novo no passo 5:

sql
UPDATE documentos SET estado = 'PENDENTE_ENVIO', atualizado_em = now()
WHERE estado IN ('COMPOSTO', 'LOCALIZADO') AND caminho_origem NOT LIKE '/srv/gesdoc/%';

5Primeira execução (manual)

bash
sudo -u gesdoc .venv/bin/python sincronizacao_factorial.py

A saída termina com o resumo. Com os dados de 14/10/2026, o esperado era:

saída esperada
{
  "pendencias": 44,
  "por_estado": {"COMPOSTO": 8, "LOCALIZADO": 12, "NAO_ENCONTRADO_FACTORIAL": 13,
                 "AGUARDANDO_ASSINATURA": 2, "DIVERGENTE_FACTORIAL": 9},
  "alertas_novos": 0
}

Os números mudam conforme as pendências do dia. O importante é não haver erro e aparecerem COMPOSTO/LOCALIZADO.

Conferir os arquivos e o banco

bash
sudo ls -R /srv/gesdoc/downloads | head -30

Cada pendência resolvida tem uma pasta com o número dela; os pacotes aparecem como doc<id>_<cpf>_<MM-AAAA>.pdf.

sql
SELECT id, doc_id, estado, caminho_origem, tamanho_bytes FROM documentos
WHERE estado IN ('COMPOSTO', 'LOCALIZADO') ORDER BY id;

todos os caminho_origem começam com /srv/gesdoc/downloads/.

Rode o mesmo comando de novo: deve terminar com "alertas_novos": 0 e sem COMPOSTO/LOCALIZADO no resumo. O que já está pronto sai da fila e nada é duplicado.

6Agendamento (cron)

A cada 2 horas, das 07h às 19h, depois da sua captura. O flock impede duas execuções ao mesmo tempo.

bash
sudo crontab -u gesdoc -e
linha do cron
0 7-19/2 * * * cd /opt/gesdoc/app && /usr/bin/flock -n /tmp/gesdoc-sinc.lock .venv/bin/python sincronizacao_factorial.py >> /var/log/gesdoc/sincronizacao.log 2>&1

Se a sua captura roda nos mesmos horários pares, desloque este para depois dela (ex.: 30 7-19/2 * * * roda aos 30 minutos).

O cron usa o horário do servidor. Confira o fuso:

bash
timedatectl
sudo timedatectl set-timezone America/Sao_Paulo   # se não estiver

Depois do primeiro horário agendado:

bash
tail -n 30 /var/log/gesdoc/sincronizacao.log

Rotação do log

Crie /etc/logrotate.d/gesdoc:

/etc/logrotate.d/gesdoc
/var/log/gesdoc/*.log {
    weekly
    rotate 8
    compress
    missingok
    notifempty
}

7API (opcional)

Só é necessária se outro sistema for disparar a sincronização sob demanda (POST /factorial/sincronizar). O agendamento funciona sem ela.

Crie /etc/systemd/system/gesdoc-api.service:

systemd
[Unit]
Description=GesDoc - API de sincronizacao Factorial
After=network-online.target
Wants=network-online.target

[Service]
User=gesdoc
WorkingDirectory=/opt/gesdoc/app
ExecStart=/opt/gesdoc/app/.venv/bin/gunicorn --workers 2 --bind 127.0.0.1:5000 --timeout 900 app:app
Restart=on-failure

[Install]
WantedBy=multi-user.target

O --timeout 900 cobre uma sincronização completa, que pode levar alguns minutos. A API escuta só em 127.0.0.1; para acesso externo, coloque um proxy com HTTPS (nginx/Caddy) na frente e não exponha a porta 5000.

bash
sudo systemctl daemon-reload
sudo systemctl enable --now gesdoc-api
curl -s http://127.0.0.1:5000/health

"database": "conectado".

Para as rotas protegidas, gere um token (vale 30 dias, assinado com a SECRET_KEY do .env) e chame a rota:

bash
sudo -u gesdoc .venv/bin/python generate_jwt_token.py
curl -s -X POST http://127.0.0.1:5000/factorial/sincronizar -H "Authorization: Bearer <token>" -H "Content-Type: application/json" -d '{"ids": [119]}'

Sem ids, processa todas as pendências elegíveis. Se a Factorial recusar a chave, a rota responde 502 e não altera nada. Logs: journalctl -u gesdoc-api -n 100 e /opt/gesdoc/app/logs/.

8Testes automatizados (recomendado)

Os testes gravam e apagam dados, então precisam de um branch de teste do Neon, nunca de produção. Crie o branch a partir de production no console do Neon e anote a connection string e o identificador do endpoint (ep-...). Crie /opt/gesdoc/app/.env.test:

.env.test
TEST_DATABASE_URL=postgresql://usuario:senha@ep-branch-de-teste....neon.tech/neondb?sslmode=require
TEST_BRANCH_ID=ep-branch-de-teste

No branch de teste, aplique o SQL do passo 4.1. Depois:

bash
sudo chmod 600 .env.test
sudo -u gesdoc .venv/bin/python -m pytest tests -q

42 passed. A Factorial é simulada nos testes; nada é chamado na Factorial real.

Operação do dia a dia

EstadoSignificaAção
COMPOSTO LOCALIZADOArquivo pronto em caminho_origemNenhuma (aguarda o envio ao Atlas)
NAO_ENCONTRADO_FACTORIALFalta item na Factorial (ex.: aviso de férias, comprovante)RH sobe o arquivo na Factorial com o tipo no nome (“aviso de férias”, “comprovante”). A próxima execução resolve sozinha
AGUARDANDO_ASSINATURADocumento existe mas não está assinadoColher a assinatura. A próxima execução resolve sozinha
DIVERGENTE_FACTORIALCPF não existe na Factorial, ou o Atlas cobra rescisão de quem está ativoConferir com o RH; a Factorial é a fonte da verdade (provável cobrança indevida no Atlas)
ERRO_COMPOSICAOUm item não é PDF nem imagemSubstituir o arquivo na Factorial por PDF

O alerta (tabela alerta) só é criado quando o estado muda; reexecutar não duplica.

Consultas úteis

sql · situação geral
SELECT d.estado, count(*) FROM documentos d JOIN documento_regras r ON r.doc_id = d.doc_id
WHERE d.aba = 'Atrasados' AND r.origem = 'Factorial' AND d.cpf IS NOT NULL GROUP BY 1 ORDER BY 1;
sql · pendências que precisam de ação
SELECT a.documento_id, d.funcionario, d.nome, a.descricao, a.criado_em
FROM alerta a JOIN documentos d ON d.id = a.documento_id
WHERE d.estado IN ('NAO_ENCONTRADO_FACTORIAL', 'AGUARDANDO_ASSINATURA', 'DIVERGENTE_FACTORIAL', 'ERRO_COMPOSICAO')
ORDER BY a.criado_em DESC;
sql · reprocessar uma pendência (ex.: 119)
UPDATE documentos SET estado = 'PENDENTE_ENVIO' WHERE id = 119;

Depois rode o passo 5, ou chame a API com {"ids": [119]}.

Segurança e dados pessoais (LGPD)

  • /srv/gesdoc/downloads guarda documentos trabalhistas com CPF: mantenha chmod 700, dono gesdoc, e só inclua no backup se o backup também for protegido.
  • .env e .env.test com chmod 600; nunca commitar (o .gitignore já cobre).
  • Os logs (logs/, /var/log/gesdoc/) podem ter nomes e CPFs: não compartilhe sem anonimizar.
  • Use só as credenciais que o Evilásio te passar por canal seguro. As antigas apareceram no histórico do git e devem estar trocadas antes de entrar em produção; se tiver dúvida, confirme com ele.

Anexo: servidor Windows

  1. Instale Python 3.10+ (marque “Add to PATH”) e Git. Clone em, por exemplo, C:\gesdoc\app.
  2. Na pasta do projeto: py -3 -m venv .venv e .venv\Scripts\pip install -r requirements.txt.
  3. No .env, use FACTORIAL_PASTA_DOWNLOAD=C:\gesdoc\downloads. No passo 4.2, troque '/srv/gesdoc/%' por 'C:\\gesdoc\\%' (no LIKE do Postgres a barra invertida precisa ser dobrada).
  4. Agendamento: Agendador de Tarefas → Criar Tarefa → disparador diário às 07:00, repetir a cada 2 horas por 12 horas → ação: programa C:\gesdoc\app\.venv\Scripts\python.exe, argumentos sincronizacao_factorial.py, “Iniciar em” C:\gesdoc\app (sem isso o .env não é encontrado) → em Configurações, “Não iniciar uma nova instância” se já estiver rodando.
  5. API: o gunicorn não roda no Windows; use .venv\Scripts\python app.py (porta 5000) como serviço via NSSM, ou dispense a API e use só o agendamento.
  6. No PowerShell, use curl.exe em vez de curl.
Dúvidas durante a instalação: fale com o Evilásio e mande a saída do comando que deu diferente do esperado. A versão completa deste guia também está no repositório, em DEPLOY.md.
